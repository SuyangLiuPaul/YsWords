## Two rulings that survived, and should be followed

### Account collision — do not detect the provider, do not build linking

Keep one-account-per-email ON and enumeration protection ON. On
`email-already-in-use` or `account-exists-with-different-credential`,
show one sentence and one button that sends a password-reset mail to the
address just typed.

The reason detection is unnecessary is the load-bearing part: **a
password reset on a Google-only Firebase account ADDS a password
credential to that same UID.** Same account, same data, both methods work
afterwards. So you never need to know which provider exists — the answer
is identical either way, the copy names no provider, and enumeration
protection stays on.

Account linking was rejected because it requires completing a Google
sign-in first, which cannot happen behind the GFW. Allowing two accounts
per address was rejected because it is the lockout being avoided, not the
fix for it: two sync silos on one address, and no merge path in the app.

Apply the same escape hatch on the sign-in path: with enumeration
protection on, a Google-only account entering a password gets a generic
`invalid-credential`, indistinguishable from a typo, so "Forgot
password?" must be visible on that error rather than buried.

### China builds — start sync lazily, never promise it

The owner verified that **email sign-in works from mainland China**. My
earlier claim that it could not was over-general: Google sign-in needs
`accounts.google.com` and the `/__/auth/*` handler, which `netlify.toml`
proxies but cannot fully rescue; email/password does not use that handler
at all and calls `identitytoolkit.googleapis.com` directly, whose
reachability is inconsistent rather than reliably blocked.

`firebaseio.com` is a different host family, so his observation is
evidence about Auth and nothing else. RTDB reachability is **unknown**,
and unknown is a question to ask the network rather than answer by fiat.

So: leave the boot path alone (`main.dart:538` unchanged) and start
`RealtimeDbSyncService` lazily after a successful sign-in. Never say
"Sync is on" before a round trip has completed — say "Last synced 14:32"
or say "Couldn't reach the sync server from your network. Your
highlights, notes and bookmarks are safe on this device. You're still
signed in," plus Retry. Local storage stays the source of truth; a sync
failure must never block or discard a local write.

**Two existing strings become lies if this ships** and must move to
runtime state rather than `kChinaMode`: `chinaCloudUnavailable`
(`settings_page.dart:1681`) and `onboardCustomizeBodyChina`. Both
currently assert flatly that cloud sync is unavailable in the China
build — false for exactly the readers who got it working.

**The owner must still enable Email/Password in the Firebase console and
check the password-reset template.** No code substitutes for that.
